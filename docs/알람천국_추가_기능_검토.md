# 알람천국 추가 기능 검토

검토일: 2026-11-13

## 1. 검토 방향

사용자 의견을 바탕으로 다음 세 가지를 후속 후보로 검토한다. 구현 확정 기획서나 작업 상태 문서는 아니며, 알라미에 전혀 없는 기능이라고 주장하지 않는다.

1. 평일·주말·특정 날짜·교대근무에 따라 달라지는 일정 알람.
2. 같이 자는 사람에게 주는 소음과 사용자 부담을 줄이는 기상 방식.
3. 알람 이름과 별도로 작성한 메모 읽어주기.

제품 방향 제안: **내 일정에 맞게, 주변에는 덜 부담스럽게 깨워주는 알람.**

## 2. 일정에 맞춰 달라지는 알람

### 해결할 상황

교대근무 전용으로 한정하지 않는다. 주말 늦잠, 하루만 다른 출근 시간, 휴가, 주·야간 교대 모두 같은 일정 체계로 다룬다.

| 상황 | 설정 예 | 기대 동작 |
|---|---|---|
| 평일·주말 기상 차이 | 월~금 07:00, 토·일 09:00 | 여러 개의 독립 알람을 반복 편집하지 않고 주간 일정을 확인 |
| 하루만 일찍 기상 | 특정 날짜만 05:30 | 그날 기상 시각을 교체하고 이후 원래 일정으로 복귀 |
| 휴가·휴일 | 특정 날짜는 알람 없음 | 기존 반복 일정을 유지하며 지정일만 제외 |
| 추가 일정 | 특정 날짜 14:00 알람 추가 | 기본 기상 알람을 유지하고 별도 일정 알람 추가 |
| 2교대·3교대 | 시작일과 순환 순서, 각 근무별 기상 시각 등록 | 요일과 무관하게 날짜에 맞춰 순환 |
| 불규칙 근무표 | 달력에서 날짜별 근무 유형 지정 | 자동 순환을 쓰지 않는 사용자도 이용 |
| 야간 근무 후 수면 | 다음 날 낮에 기상 | 근무 날짜와 실제 알람 날짜를 명확히 구분 |

### 제안하는 구성

- **기본 주간 일정:** 요일별 기상 시각. 동일한 요일을 묶어 빠르게 설정.
- **날짜별 예외:** 특정 날짜의 시각 변경·건너뛰기. 적용 뒤 기본 규칙으로 자동 복귀.
- **순환 일정:** 기준 시작일과 근무 순서 등록. 예: 주간→주간→야간→야간→휴무→휴무. 이는 예시이며 특정 업종의 표준 교대표가 아니다.
- **근무 유형:** 주간·오후·야간·휴무 등의 이름과 기상 시각을 사용자 지정. 2교대·3교대라는 이름만으로 실제 순서를 자동 결정하지 않는다.
- **달력 확인:** 향후 날짜별 실제 울릴 시각과 적용 이유를 표시. ‘주말’, ‘날짜 변경’, ‘야간 근무’ 등을 구분.

### 우선 적용 규칙 제안

1. 해당 날짜의 명시적 예외(시각 교체 또는 건너뛰기).
2. 사용자가 선택한 기본 일정 방식(주간 또는 순환 또는 수동 근무표).
3. 별도 추가 알람은 기본 기상 일정과 독립적으로 유지.

주간 일정과 순환 일정을 동시에 자동 합성하지 않는 구성을 우선 검토한다. 날짜 예외의 ‘교체’와 ‘추가’를 구분해, 일찍 일어난 뒤 원래 알람이 다시 울리는 일을 방지한다.

### 화면 예시

> 내일 09:00 · 주말 일정<br>
> 월요일 05:30 · 이번 날짜만 변경<br>
> 화요일 07:00 · 기본 일정으로 복귀

### 먼저 정할 사항

- 야간 근무의 ‘근무일’을 어느 날짜로 볼지, 기상 시각의 당일·다음 날 표시 방식.
- 순환 순서를 바꿀 때 이번 날짜부터 적용할지 다음 주기부터 적용할지.
- 해외 이동 시 현지 시각을 유지할지 기존 시간대를 유지할지.
- 공휴일은 초기에는 사용자 지정으로 처리하고, 국가별 공휴일 자동 연동은 별도 검토.
- 일정별 소리·미션을 별도로 둘지 공통 설정을 상속할지.

### 현재 구조에 대한 기술 검토

현재 `AlarmSchedule`은 시각과 요일을 저장하며, `Alarm` 하나와 시스템 알람 ID 하나가 연결된다. 날짜 예외·순환 일정은 이 범위를 확장한다. 사용자가 만든 일정 규칙과 실제 예약 회차를 구분할 필요가 있다.

특히 앱을 장기간 열지 않아도 예약이 이어져야 한다. 가까운 며칠만 미리 예약하고 앱이 매일 실행될 것으로 가정하는 방식은 피한다. 지원 가능한 순환 예약 범위·시스템 예약 한도·앱 미실행 시 예약 보충 가능성을 기술 검증한 뒤 제공 범위를 결정한다. 현재 최대 10개 제한도 사용자가 만든 일정 수와 파생 예약 수 중 무엇을 세는지 재정의가 필요하다.

## 3. 같이 자는 사람을 배려하는 알람

### 목표

‘무조건 작은 소리’보다 **깨우는 데 필요한 소리의 크기·지속 시간·발생 횟수를 줄이는 것**을 목표로 삼는다. 사용자가 놓칠 때의 대응도 함께 선택할 수 있어야 한다.

| 후보 | 사용자 경험 | 검토 사항 |
|---|---|---|
| 부드러운 소리 | 자극적인 소리 대신 차분한 음색 선택 | 음색과 실제 시스템 음량 제어는 별개 |
| 단계적 기상 | 짧고 부드러운 자극 → 미응답 시 일반 알람 | 앱 미실행·잠금 상태에서도 전환 가능한지 검증 |
| 반응 후 짧은 정숙 시간 | 사용자가 미션을 시작하면 잠깐 조용히 수행, 시간 초과 시 다시 울림 | 단순 터치로 영구 해제되지 않도록 후속 예약·재시작 복구 검토 |
| 조용한 미션 | 수학·따라쓰기 등 움직임 소음이 적은 미션 추천 | 흔들기·걷기보다 주변 소음이 적을 수 있으나 실제 사용 검증 필요 |
| Apple Watch 진동 우선 | 손목 자극 후 미응답 시 iPhone 알람 | Watch 앱 필요 여부, 착용·배터리·연결·OS 지원 검증 |
| 이어폰 우선 | 연결된 개인 기기로 먼저 안내 | 연결 해제·배터리 소진·스피커 전환·장시간 착용 상황 검증 |

위 표는 제품 후보이며 기술 구현 가능성을 확정한 목록이 아니다. 특히 ‘완전 무음으로 확실한 기상’, ‘Watch 착용 여부 자동 인식’, ‘AlarmKit 음량을 앱에서 자유롭게 제어’는 현재 약속하지 않는다.

### 제안하는 설정 흐름

1. 조용한 기상 사용 여부 선택.
2. 먼저 시도할 방식과 대기 시간 선택(지원 검증된 방식만 노출).
3. 미응답 시 일반 알람으로 전환할지 명시적으로 선택.
4. 저장 전 테스트로 사용자가 실제 소리·진동을 확인.
5. 연결 기기가 필요한 방식은 취침 전 준비 상태와 실패 시 동작을 확인.

기존 확실한 기상 모드와 사용자가 선택하는 조용한 기상 모드를 구분하는 방안을 검토한다. 조용한 기상에서 미션 중 잠시 소리를 줄이는 정책은 기존 ‘미션 완료 전 지속 재생’ 요구를 바꾸므로 기획 확정이 필요하다.

### 기술 검증의 경계

Apple 공식 AlarmKit 구성은 시스템 알람의 소리 선택을 제공한다. 이 사실만으로 알람별 음량·임의 진동 패턴·Watch 우선 전달까지 보장되지는 않는다. 앱 안 오디오와 잠금·종료 상태의 시스템 울림은 나누어 검증한다.

출처: [Apple AlarmKit 알람 구성](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration/alarm(schedule:attributes:stopintent:secondaryintent:sound:)), [WWDC25 AlarmKit 소개](https://developer.apple.com/videos/play/wwdc2025/230/).

## 4. 메모 읽어주기

### 조사 보완

- 사용자가 알라미 앱에서 유료 기능으로 확인한 항목이다.
- 공식 iOS 공지도 표시용 이름과 Label Reminder용 메모 필드를 구분한다.
- 알라미에 없는 기능이 아니라, 알람천국에 추가할 편의 기능 후보로 분류한다.
- 출처: [알라미 공식 iOS 이름·메모 안내](https://alarmy-ios.zendesk.com/hc/en-us/articles/51193686070169--Your-alarms-can-have-names-now-finally).

### 알람천국 제안

- 표시용 알람 이름과 읽을 메모를 별도로 입력.
- 예: 이름 ‘이른 출근’, 메모 ‘오늘은 여섯 시 반에 나가야 해요. 출입증 챙겨요’.
- 알람별 읽기 켜기·끄기, 입력 언어에 맞는 한국어·영어 음성, 저장 전 들어보기 검토.
- 언제 읽을지 구분: 처음 울릴 때 / 앱 진입 후 / 미션 완료 후. 초기 구현 후보는 제어하기 쉬운 앱 진입 후 안내.
- 조용한 기상에서는 스피커 메모 읽기를 기본 해제하는 방안 검토. 소음을 줄이는 설정과 음성 안내가 충돌하지 않도록 한다.
- 날짜 예외에도 메모를 붙여 ‘왜 오늘 일찍 일어나야 하는지’를 전달하는 방향 검토.
- 잠금화면·앱 종료 상태의 음성 합성은 별도 검증. 앱 안에서 읽힌다는 사실만으로 시스템 알람에서도 읽힌다고 보장하지 않는다.

## 5. 개발 순서 제안

1. **일정 기본 확장:** 평일·주말 기상 시각 + 특정 날짜 변경·건너뛰기 + 향후 일정 확인.
2. **교대근무 확장:** 시작일·근무 유형·순환 순서와 날짜별 수정. 장기간 앱 미실행 예약 검증을 먼저 수행.
3. **조용한 기상 기술 검증:** 실제 기기에서 잠금·백그라운드·종료 상태별 가능한 동작 확인. 검증 결과로 첫 제품 범위 결정.
4. **메모 읽어주기:** 앱 내 읽기부터 검토하고 일정 예외·조용한 기상과 연결.

조용한 기상의 실현 가능성이 제품 방향을 바꿀 수 있으므로 기술 검증은 일정 기능 설계와 병행할 수 있다. 앱 구현·확정 기획서 변경은 이 문서 작성 범위에 포함하지 않는다.
